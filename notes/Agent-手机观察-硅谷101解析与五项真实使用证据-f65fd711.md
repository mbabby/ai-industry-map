# Agent 手机观察｜硅谷101解析与五项真实使用证据

整理日期：2026-10-21。资料范围：用户提供的硅谷101视频转录、随后关于 Agent 手机的讨论，以及补充检索到的原始实测与研究资料。

这是一份学习与选题笔记，不是手机购买建议，也不是对全部产品作出的统一排名。不同月份、设备版本和测试协议不能直接混比。

## 一、这次讨论从哪里出发

节目讨论的变化是：过去用户自己打开应用、找到入口、逐步操作；Agent 手机尝试让用户先说目标，再由助手理解屏幕、调用应用或接口，把几个步骤连起来完成。

用户在讨论中进一步要求寻找另一面的证据：跨应用任务成功率、实际节省的时间、人工接管次数、长期耗电，以及出错之后能否恢复。这个追问把注意力从“可以演示什么”转向“日常使用究竟付出了多少代价”。

原始材料：用户提供的硅谷101转录文本，开头为“最近，手机大战又打响了……”。节目中的产品介绍、厂商观点与以下补充研究分开记录，不把节目判断直接视为经验证实的结论。

## 二、节目的主线与需要保留的边界

### 为什么各家现在都在做 Agent 手机

节目把几件事放在一起：传统硬件升级越来越难带来明显的新鲜感，存储成本变化影响整机成本；与此同时，端侧计算、模型效率和端云协作在进步，让助手承担更多任务成为可能。

这是一套合理的供给侧解释，但厂商需要新的卖点，并不能单独证明消费者需要换一部新手机。部分能力也可能通过系统或软件升级进入旧设备。关于存储成本，可参考 [Counterpoint 的手机物料成本研究](https://counterpointresearch.com/en/insights/Memory-Price-Surge-Triggers-Shifts-in-Smartphone-BOM-Structure)。

### 产品并不是只有两条互斥的路

可以区分系统级助手与应用内助手，但不能简单分成“操作系统路线”和“超级 App 路线”后就认为各家完全不同。更有用的三个观察维度是：

- **入口在哪里：** 系统按键、语音入口，还是一个独立应用。
- **能获得哪些权限：** 读当前屏幕、读取个人数据、跨应用操作、对外发送或支付，权限深度不同。
- **怎样执行：** 模拟点击图形界面，调用结构化接口，或者两者结合。

系统集成能提供更多上下文与操作能力，应用或服务接口则可能更稳定，但它们都需要合作、授权和结果核验。谷歌、苹果、努比亚与豆包的布局可以放在这些维度上理解，不必强行贴成单一路线。

可回查的官方材料：[Gemini 多步骤任务介绍](https://blog.google/innovation-and-ai/products/gemini-app/android-multi-step-tasks/)、[Apple App Intents](https://developer.apple.com/documentation/appintents)、[努比亚相关发布](https://www.zte.com.cn/china/about/news/20260916C1.html)、[豆包手机助手](https://o.doubao.com/)。其中 Gemini 链接是二月的早期预览说明，不能把当时范围当作十月的完整功能清单。

### 硬件进步解决了哪些问题

低功耗唤醒、CPU/GPU/NPU 分工、减少数据搬运、模型压缩及端云协作，有助于改善运行成本、响应速度和设备负担。[高通的 Hexagon NPU 架构介绍](https://www.qualcomm.com/news/onq/2026/09/hexagon-npu-agentic-ai-architecture)可以帮助理解这些工程方向。

但处理器更快，不等于任务判断更准确；芯片缓存、运行时 KV cache 与长期个人偏好记忆，也不是同一种“记忆”。对偏好的记录还需要来源、适用范围、更新、删除与用户确认机制。

## 三、五个问题：已有证据和缺口

| 问题 | 目前能看到什么 | 仍不能据此认定什么 |
| --- | --- | --- |
| 任务能否完成 | 有批量媒体测试，也有真实应用研究基准和成功个案。 | 不能把不同任务集的分数当成统一的跨应用成功率，更不能直接外推到任意日常请求。 |
| 是否节省时间 | 已有点单、打车、整理资料的实际用时记录。 | 多数没有同一任务的人工计时对照；任务总耗时与用户主动投入时间需要分别测量。 |
| 需要接管多少次 | 报道记录了确认、补充信息，以及失败后人工处理。 | 缺少总任务数和一致分类时，不能给出可靠的接管频率。 |
| 长期耗电如何 | 有研究项目采集真实手机的电量与温度日志。 | 普通整机续航成绩不是 Agent 的增量耗电；公开的长期、对照使用证据仍不足。 |
| 出错能否恢复 | 有绕回正确页面、自行重规划的个案，也有专门研究。 | 界面操作恢复不等于撤销已发出的消息、订单或付款。 |

### 1. 批量商业产品测试：有价值，但必须标明时间

[21世纪经济报道：万字详解智能体2.0](https://m.21jingji.com/article/20260224/herald/aa3efebf718749a130f4edfb8a2acff7.html)，发表于 2026-02-24。

报道测试豆包、智谱、荣耀、华为、小米、OPPO、vivo 七家助手，共70次任务尝试，整体成功约20%；另有39%执行中断、24%直接失败并退回问答。它展示了任务规划、入口变化、平台限制等实际障碍。

使用限制：这是二月的综合样本，不是豆包单独的成绩，也不是十月整个行业的水平；任务不全是严格跨应用，公开材料不足以重建完整版本、重复次数和逐次日志。不要把这些分类强行凑成100%，或把约20%换算成未经证实的精确成功次数。

### 2. 时间：点单能完成，并不意味着机器更快

[Tom’s Guide 原始体验](https://www.tomsguide.com/phones/samsung-phones/i-just-asked-gemini-on-the-galaxy-s26-to-order-dunkin-donuts-for-me-and-24-minutes-later-it-got-delivered-to-my-door)，作者 John Velasco，发表于 2026-03-13。

他用 Galaxy S26 上的 Gemini，经 DoorDash 点咖啡和甜甜圈，助手完成指令约花2.5分钟。作者估计自己可能不到30秒就能操作完，但这不是人工与 AI 的配对计时实验。标题里的24分钟包括配送，不能当作 Agent 执行时长。

这个个案适合引出问题，不适合证明所有 AI 点单都慢。如果用户发出指令后可以安心去做别的事，机器慢一些也可能有价值；反过来，即使执行快，若必须盯着纠错，节省的注意力仍然有限。这是我们的分析，不是该报道测出的结论。

### 3. 较新的产品个案：已经出现完整工作流

[IT之家：努比亚 NaviX Ultra 体验](https://m.ithome.com/html/1003190.htm)，作者马卡，发表于 2026-09-16，测试系统 ObricUI v[IP地址已隐去]。

报道中的滴滴任务约2分钟进入确认环节，最终仍需用户确认；搜索相关新闻、整理文档并发送飞书的一个任务约1分钟，报道描述其间未额外人工介入。

限制：这是所展示的任务个案，没有完整尝试总数、重复测量、人工基线与耗电对照。涉及敏感动作的必要授权，不应一律记为故障接管。应用可用性也受版本、地区和平台政策影响。

### 4. 恢复与接管：真实体验里已经可以看见差异

[The Verge 五天体验](https://www.theverge.com/tech/898282/gemini-task-automation-uber-doordash-hands-on)，发表于 2026-03-21：一次餐食任务约9分钟，助手曾自行纠正路径；也有因权限或旧地址卡住、需要人处理后重来的情况。报道没有总尝试数，不能由此计算接管率。

### 5. 高分研究基准：看成绩，也要看分母

[Qwen-UI-Agent 技术报告](https://arxiv.org/html/2607.28227v1)，发布于 2026-07-30。

MobileWorld-Real 包含409项任务、104个真实 Android 应用、7类领域；报告给出 Qwen-UI-Agent 27B 的92.2%成绩。

关键条件：评测允许询问用户和必要接管；验证码、登录失效、网络或服务不可用等环境错误被排除出成功率分母，结果主要由模型裁判评定。这是作者构建的研究评测，不是某款量产手机的独立日用测试，也不是“所有请求无人介入完成92.2%”。

不能把这个成绩和二月媒体70次尝试的约20%放在同一条曲线上，当作行业从20%进步到92.2%的证据。

### 6. 失败恢复研究：值得关注，尚不能等同于交易可撤销

[MAPLE 论文](https://arxiv.org/html/2505.23596v1)，发布于 2025-05-29。

研究在真实 Pixel 7 Pro 上，用持久状态、前后置条件与恢复规划帮助助手找回执行路径。在两组小型任务中，分别恢复了32个失败子任务中的23个、63个中的42个，恢复率约71.88%和66.67%。

这是失败子任务的恢复比例，不是整项任务成功率，也不是商业助手的人工接管率。它证明了恢复机制可以被专门设计和评测；并未证明已发送消息、已提交订单和资金交易都能安全撤回。

### 7. 长期耗电：目前最需要补齐的一项

[AndroidLife 研究项目](https://androidlife-website.vercel.app/)公开了真实手机任务与电量、温度等日志，说明已有研究开始观察 GUI Agent 的设备负担。

但它并不构成量产助手连续数周的消费级对照实验，也没有足够清晰的人工执行或关闭 Agent 基线。“28天”任务结构不能当作实际跑了28天。部分公开运行记录还存在时间口径问题，因此本笔记不采用其中的耗电数值作结论。

整机五小时续航剩余电量、芯片宣称的能效提升，同样不能直接回答：打开这个助手后，普通用户一天多消耗多少电。

## 四、讨论中逐渐形成的分析框架

以下是讨论归纳与待检验的判断，不把它们冒充成用户逐条确认的长期观点。

### 先看能不能交出注意力

任务总耗时之外，应该单独记录用户主动投入的时间：描述需求、补充信息、确认关键动作、检查结果、发现错误和修复错误。对 Agent 来说，“用户可以暂时不管它”可能比“每一步点击都更快”更有意义，但这需要实测，不能靠想象兑现。

### 把三种人工参与分开

- **需求澄清：** 用户没有说清地址、预算、时间，系统需要补问。
- **必要授权：** 下单、付款、发送敏感信息前请用户确认。
- **故障接管：** 系统走错、卡住或无法继续，需要人替它排障。

前两种不一定是产品失败，第三种的频率、耗时和修复成本则应单独披露。完全没有确认，也不必然优于恰当确认。

### 恢复不只是回到上一页

至少应分成：回到可继续操作的界面；确认动作到底有没有完成；避免重复发送或重复下单；对已经发生的外部后果提供撤回、补救或清楚提示。

例如提交订单后超时，不应立即把超时当成失败再提交一次，而应先查订单状态。这是一个工程设计示例，不是上面几款手机已经全面实现的能力。

### 平台合作和信任也决定产品上限

跨应用执行还受登录状态、验证码、接口开放、平台风控和商业关系影响。系统获得更深权限，不能自动保证所有服务都愿意配合。

同时，应分别处理“看见屏幕”“长期保存”“上传云端”“代表用户行动”的授权。局部推理或本地摘要，不等于所有隐私问题已经解决。

## 五、后续看新产品时，怎样继续找证据

1. 先问测试对象：模型、研究型 Agent，还是消费者实际能用到的手机助手？注明日期、地区、设备和版本。
2. 要完整分母：尝试总数、成功、失败、放弃、环境错误、接管各是多少；不要只看精选成功片段。
3. 同时看端到端时间与用户主动投入时间；人工对照尽量使用同一任务、同一账户和相近网络。
4. 把纯系统任务、单应用任务、跨应用任务，以及需要个人历史信息的任务分开。
5. 电量研究需要可比的使用负载、温度、充电和网络条件；记录端侧与云端分工，避免把调用云模型说成全部本地计算。
6. 对失败恢复，优先关心错误是否被发现、状态是否可核查、是否产生重复动作、用户承担什么补救成本。

当前更稳妥的结论是：Agent 手机已经有可以完成真实任务的产品和研究证据，但证据分散，协议不同。距离证明“长期、普遍、省心地替用户办事”，还需要更完整的日用评测。这既不是否认进步，也不宜提前宣布它已取代现有应用使用方式。
